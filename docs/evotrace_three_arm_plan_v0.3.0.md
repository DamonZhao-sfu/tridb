# EvoTrace × GEM × OpenEvolve — 实验方案 v0.3.0

- 日期：2026-08-25
- 状态：**设计已修订，待执行**
- 前一版：`evotrace_three_arm_plan_v0.2.0.md`（含附录 A 的 Phase P / Phase 0 执行记录）
- 修订依据：v0.2.0 按原设计跑出的第一批真实数据

## 为什么有 v0.3.0

v0.2.0 的设计跑出了 2 对完整 cell。数据显示 **三处设计缺陷**，其中两处会让实验
即使完美执行也得不出结论。这一版是对那三处的修正，不是参数微调。

| # | 缺陷 | 证据 | 修正 |
|---|---|---|---|
| 1 | **主指标在本任务上没有分辨力** | 语料自己的 run 在第 9 轮就达到最终分的 94.7%，第 25 轮 100%。终点最高分在设计上就几乎是常数 | §2 换主指标 |
| 2 | **任务集合按"有没有 evaluator"选，不是按"有没有改进空间"** | `first_autocorr_ineq` 的可改进余量 **0.14%**（起点 0.9912 / 语料最佳 0.9926）。在它上面测记忆＝测噪声 | §3 按余量筛选 |
| 3 | **注入完整的、严格更好的程序＝把检索变成答案发放器** | arm B 的 `copy_rate` 21.8%（对照 10.1%）。检索谓词 `fitness ≥ parent` 保证每轮递一份更好的成品，照抄是模型的最优策略而非缺陷 | §4 增加注入形态轴 |

**不属于设计缺陷、保持不变的**：arm 结构（两个 cell 仅差 `retriever` 一个字段，已逐字段
验证）、指标溯源（只用 AlphaEvolve 原生的两个）、六道闸门体系（本轮抓到 8 个会让实验作废
的实现缺陷，见 v0.2.0 附录 A）。

## 2. 主指标改为"到达阈值所需轮数"

### 2.1 为什么换

v0.2.0 的主指标是终点最高分。实测 `circle_packing`：

```
轮次       0       4       9      19      39      59      79      99
arm gem   0.4279  0.4842  0.9256  0.9256  0.9256  0.9256  0.9256  0.9256
arm none  0.0000  0.8941  0.8941  0.8941  0.8941  0.8941  0.9108  0.9108
```

终点差 **0.015**（几乎无意义）；到达时间差 **8 倍**（第 9 轮 vs 第 79 轮）。
信息全在曲线前段，而主指标只读了最后一个点。

### 2.2 新的指标集

| 指标 | 定义 | 溯源 |
|---|---|---|
| **`iterations_to_threshold`（主）** | 首次达到 `seed + α·(corpus_best − seed)` 的轮次，α ∈ {0.25, 0.5, 0.75, 0.9}。未达到记为右删失 | **我们的自定义指标**。AlphaEvolve 只有定性表述（FunSearch "millions of samples" vs AlphaEvolve "thousands suffice"），必须如此标注 |
| **best-so-far vs 计算预算 曲线** | 不变，仍是 Figure 8 形状 | AlphaEvolve 原生 |
| **per-task 最佳分 → 分类率** | **保留但降级为次要**。实测两个 arm 全部落在 `below_corpus_best`，已退化成常数 | AlphaEvolve 原生 |

阈值用 **相对余量** 而非绝对分数，因为各题的起点和天花板差异极大（起点 0.0 到 0.9912）。

### 2.3 右删失必须显式

未在预算内达标的 cell **不能记为"轮数 = 预算上限"**——那会把"差一点"和"完全没戏"
混为一谈。记为删失，报"达标比例"与"达标者的中位轮数"两个数。

## 3. 任务集合按可改进余量筛选

`余量 = (corpus_best − seed_fitness) / corpus_best`：

| task | 起点 | 语料最佳 | 余量 | 纳入 |
|---|---:|---:|---:|---|
| heilbronn_triangle | 0.0000 | 0.9837 | **1.0000** | ✅ 主 |
| heilbronn_convex_13 | 0.0104 | 0.9090 | **0.9885** | ✅ 主 |
| circle_packing | 0.3642 | 0.9962 | **0.6344** | ✅ 主 |
| third_autocorr_ineq | 0.5784 | 0.9968 | 0.4198 | ⚠️ 次要 |
| signal_processing | 0.4990 | 0.7505 | 0.3351 | ❌ 无 evaluator |
| second_autocorr_ineq | 0.9677 | 1.0412 | 0.0705 | ❌ 余量过小 |
| uncertainty_ineq | 0.8804 | 0.8934 | 0.0145 | ❌ 余量过小 |
| first_autocorr_ineq | 0.9912 | 0.9926 | **0.0014** | ❌ 余量过小 |

**门槛 0.30。** 低于它的题上，任何 arm 差异都落在 evaluator 自身的库版本漂移
（v0.2.0 附录 A.6 实测 5e-5 ~ 4.6e-3）与单次运行方差之内。

**结果：主任务 3 道 + 次要 1 道，不是 v0.2.0 写的 7 道。**

> 这进一步削弱 §6.1 已声明的统计效力：3 道题 × 单 seed。必须如实报告，
> 并且**不得**用 "7 tasks" 描述本实验。

## 4. 注入形态成为实验轴

### 4.1 问题

检索谓词是 `is_valid AND fitness >= parent_fitness` —— 每轮递给模型一份
**比它手头严格更好的完整程序**。到这一步，照抄是最优策略，不是模型的缺陷。

实测 `copy_rate`：arm B **21.8%** / arm A 10.1%；`distinct/iter` 0.772 / 0.899。
arm B 在两道题上的领先（+0.015、+0.019）都伴随更高的照抄率。

**这样测出来的是"检索准不准"，不是"记忆帮 agent 想得更好"。**
Experience Graph 论文讲的 reuse 是后者。

### 4.2 两种注入形态

| 形态 | 渲染什么 | 能否被照抄 |
|---|---|---|
| `code`（v0.2.0 现状） | 程序源码 | 能，实测 21.8% |
| **`changes`（新增）** | 该程序的 `changes_description`（"改成贪心顺序放置"） | **物理上不能** |

OpenEvolve 原生支持（`prompt.programs_as_changes_description`），检索路径完全相同，
所以两者干净地隔离了「复用答案」与「复用方法」。

**覆盖率限制**：math 域 5,403 个程序中 **4,443（82.2%）** 有 `changes`，其余渲染为
`<missing changes_description>`。逐轮计数（`retrieval_telemetry.missing_changes`），
**不静默丢弃** —— 丢弃会让实际注入率低于设定值，而注入率是自变量。

## 5. 迭代预算 100 → 40

语料实测：`circle_packing` 第 40 轮已 100%，四道低余量题第 10 轮 ≥98.7%。
但 heilbronn 系第 40 轮仍只到 0.80，仍在爬。

**取 40。** 理由：覆盖 circle_packing 的完整轨迹；给 heilbronn 系留出主指标
（到达阈值轮数）所需的分辨率；相比 100 轮省 60% 的 GPU 与 evaluator 时间——
后者正是 v0.2.0 那批 8/14 个 cell 卡死的直接成本。

超出 40 轮的部分对**主指标无贡献**：所有 arm 的达标事件都发生在前 25 轮。

## 6. 实验矩阵

```
主任务   heilbronn_triangle / heilbronn_convex_13 / circle_packing      (3)
arm      none                                                          (1)
         gem × {inject_as: code, changes} × {rate: 0.1, 0.5, 1.0}       (6)
seed     1
iters    40
                                                              → 3 × 7 = 21 cells
```

`none` 是注入率 0% 点，不沿 rate 轴展开。

按已完成 cell 的实测（100 轮 26–36 分钟）折算，40 轮约 **11–15 分钟/cell**；
21 cells、6 并发 ≈ **1 小时**。

**次要任务** `third_autocorr_ineq`（余量 0.42）单独跑一遍主对照
（`none` / `gem@100%code` / `gem@100%changes`），作为余量敏感性的检查，不进主表。

## 7. 新增指标

在 v0.2.0 §0 之上：

| 指标 | 字段 | 作用 |
|---|---|---|
| **到达阈值轮数** | `iters_to_25/50/75/90` | **新主指标**，右删失显式标注 |
| **可改进余量** | `headroom` | 任务筛选依据，也是阈值的分母 |
| **缺失 changes 率** | `missing_changes` | `--inject-as changes` 的覆盖率限制 |
| 照抄率 | `copy_rate` | 不变，仍是有效性前提 |
| 精确复现率 | `reproduced_injected_rate` | 不变 |
| 三种注入率 | `coverage` / `slot_share` / `retrieval_yield` | 不变 |

## 8. 保留的限制（未因本次修订而改变）

1. **单 seed**，无误差棒，差异**不得称显著**（v0.2.0 §6.1）
2. **无 Oracle arm**（v0.2.0 §6.2）。触发条件已实际发生 —— 两个 arm 全部
   `below_corpus_best` —— 但保留原决定。**一旦 §2.2 的新主指标也无法区分 arm，
   补 Oracle 是第一优先动作**，而不是调检索参数
3. **arm C（Polyglot）未接入**：需要 Milvus + Neo4j，`test_e1_parity.py` 三个用例
   因 `:19530` 不可达而失败。arm C 在 `run_arm` 中被硬性拒绝，直到
   `gate_polyglot_parity` 通过
4. **ALE 的 10 道题未纳入**，需要 `ale_bench` + 测试数据 + C++ 工具链
5. 四道优化器 evaluator 有 5e-5 ~ 4.6e-3 的库版本漂移；本版的余量门槛 0.30
   已把受影响最重的三道题排除在主表之外
